# Runbook (owner's notes)

How the public demo is run: Render (API, Docker) + Supabase (PostgreSQL) + GitHub Pages (frontend) + Brevo (e-mail).
Everything here is about the free tiers. Statements about what a provider does come from its documentation at the time of
writing and can change; they are marked "provider behaviour". For configuration keys see the table in the
[README](../README.md#2-configure-secrets), for the SQL scripts [`deploy/`](deploy).

## 1. Minimum environment on Render

Docker runtime, built from the root `Dockerfile`. Health check path: `/health`.

| Variable | Needed | Value |
|---|---|---|
| `JwtSettings__Key` | yes | at least 32 bytes, e.g. `openssl rand -base64 48` |
| `Encryption__Key` | yes | base64 of exactly 32 bytes, e.g. `openssl rand -base64 32` |
| `ConnectionStrings__DefaultConnection` | yes | the Supabase **session pooler** string (section 3), `Host=...` form or `postgresql://` URI |
| `Brevo__ApiKey`, `Brevo__SenderEmail` | for e-mail | a sender verified in Brevo; without them no mail is sent and password reset cannot be completed |
| `Demo__ExposeOtp` | demo only | `true` shows login and transfer codes on screen (and writes every code to the log). Never with real data |
| `GeminiSettings__ApiKey` | for the AI chat | without it (and without Ollama, which Render does not have) the bot answers with the canned "offline" text |
| `Cors__AllowedOrigins__0` | only for a fork | defaults to `https://alonessam.github.io` |
| `AllowedHosts` | recommended | the service's host name, e.g. `smartbank-fintech-api.onrender.com`. Check that the health check still passes after setting it |

`ASPNETCORE_ENVIRONMENT` stays unset (Production). The image listens on port 8080 and trusts the proxy's
`X-Forwarded-*` headers; never expose it without a proxy.

## 2. Rotating keys (what happens)

- **`JwtSettings__Key`**: every access token stops validating at once, so everyone is signed in again at the next
  request. Refresh tokens are random values kept as hashes in the database, so they survive; the web app then refreshes
  silently with the new key. In practice users see at most one failed call. Do this at once if the key may have leaked.
- **`Encryption__Key`**: all stored card numbers were encrypted with the old key and cannot be read any more (the API shows
  an empty number for them, it does not crash); the duplicate-card hash is also derived from this key. There is no
  multi-key support (DEFENSE T4). For the demo, clear the cards or accept that existing ones become unreadable.
  Do not rotate it casually.
- **Supabase password / `ConnectionStrings__DefaultConnection`**: change it in Supabase first, then on Render (the service
  restarts when a variable changes). Between the two steps the API cannot reach the database.
- **Brevo key**: create the new key, set `Brevo__ApiKey`, delete the old key.
- Where to generate: `scripts/dev-secrets.ps1 -Rotate` / `scripts/dev-secrets.sh --rotate` is for your **local** user-secrets
  only. Production keys are generated by hand (the commands above) and pasted into Render; never commit them.

## 3. Database (Supabase)

- **Run the SQL scripts in order, once each, before deploying the matching API version**: `v1.1`, `v1.2`, `v1.3`, `v1.3.2`
  (README, "Upgrading a PostgreSQL deployment"). A fresh database uses `00-baseline-postgres.sql` only. Paste the file
  into the Supabase SQL editor and run it. Afterwards run `schema-check.sql` and compare with the model if anything is
  odd (it also lists the production foreign keys).
- **Connection string**: use the **session pooler** (host `aws-...pooler.supabase.com`, port **5432**, user
  `postgres.<project-ref>`). The direct database host is IPv6-only (provider behaviour) while Render's free tier is
  IPv4-only, so it does not connect. The **transaction pooler** (port 6543) is not supported: it does not work with the
  way the API uses connections (DEFENSE T14).
- **Paused project**: a free Supabase project is paused after about a week without activity (provider behaviour). Then the
  API answers 500 on every database call and `/health/ready` is `Unhealthy`, while `/health` is still `Healthy`. Restore:
  open the project in the Supabase dashboard, press *Restore project* and wait a few minutes; no redeploy is needed, the
  API reconnects by itself. Any database use counts as activity, so a regular ping (section 5) keeps it awake.
- **Backups**: the free plan has no backups you can rely on (provider behaviour). Demo data is fake, but the schema and
  the agent accounts are worth keeping. Idea: a scheduled GitHub Actions workflow (weekly cron) that runs
  `pg_dump "$SUPABASE_DB_URL" --format=custom` and uploads the file as a private artifact, with the connection string in a
  repository secret. Not set up yet.
- **Rollback**: the SQL scripts are forward-only; there are no "down" scripts. Rolling back the API on Render
  (*Manual Deploy* of an earlier commit) is safe only when the older version can live with the newer schema. The scripts
  mostly add columns with defaults and indexes, so the previous image usually still runs, but two changes can bite:
  v1.3 adds unique indexes (one credit card per customer, one saved entry per recipient) that an older API would
  violate in a race, and v1.2 changes the time columns to `timestamptz` (whether a v1.1 API still writes to them cleanly was
  not tested). Take a `pg_dump` before running a script.

## 4. Render (API)

- **Cold start**: a free web service spins down after about 15 minutes without traffic and needs roughly a minute to
  start again (provider behaviour). The first request after a pause is slow; the README warns visitors.
- **Standing orders** run in a background worker of the API process. While the instance sleeps nothing runs; due orders
  are executed (late, not lost) once it is awake again.
- **Keep-warm**: an external uptime monitor (for example UptimeRobot, free) that calls `https://<service>/health` every
  5 minutes keeps the instance awake, but a free instance has a monthly hour limit (provider behaviour) that one
  always-on service stays under only when it is the only one in the account. Use `/health/ready` once a day instead if
  you only want to keep Supabase awake.
- **Deploys** come from `main` (auto-deploy). Order for a release: SQL script, API deploy, then
  `scripts/deploy-pages.ps1 -Push` (the web app needs the new API).
- **Logs**: Render's log view only (short retention on the free plan). SQL statements are not logged at the default
  level; set `Logging__LogLevel__Microsoft.EntityFrameworkCore.Database.Command=Information` to see them while debugging.

## 5. Health and monitoring

| Endpoint | Checks | Use it for |
|---|---|---|
| `GET /health` | nothing (the process answers) | Render health check, keep-warm ping |
| `GET /health/ready` | opens a database connection | "is the database reachable?", paused Supabase |

Both return only `Healthy` or `Unhealthy`; details go to the log. A paused database makes `/health/ready` slow before it
fails (the connection attempt has to time out), so do not use it as the platform health check: a database outage would
restart a perfectly good process (DEFENSE T7). Suggested monitoring: one uptime monitor on `/health` (5 minutes) and one
on `/health/ready` (alert by mail). Beyond that there are no metrics or tracing.

Quick check of the headers after a deploy (verified on the live API on 2026-10-07):
`strict-transport-security: max-age=15552000`, `x-content-type-options: nosniff`, `x-frame-options: DENY`,
`content-security-policy: default-src 'none'; frame-ancestors 'none'`.

```bash
curl -sD - -o /dev/null https://smartbank-fintech-api.onrender.com/health
```

## 6. E-mail (Brevo)

- Free plan: 300 mails a day (provider behaviour). One-time codes are sent in the background without retry.
- **When the limit is reached or Brevo is down**: the API still answers "code sent"; the mail never arrives. The user waits
  for a code that does not come; password reset cannot be completed and a 2FA login or transfer cannot be confirmed
  (without `Demo__ExposeOtp`). The log has `Could not e-mail the ... code to user ...` (no address, no code).
- A sender such as `@gmail.com` cannot be signed by Brevo, so mail may land in spam; a domain of your own with SPF and DKIM
  fixes that.
- Start of the API fails by design if `Brevo__ApiKey` is set without `Brevo__SenderEmail`.

## 7. Costs and limits at a glance

| Service | Free-tier limit that matters (provider behaviour) | What happens |
|---|---|---|
| Render | spins down when idle; monthly instance hours | cold start of about a minute; the service is suspended if the hours run out |
| Supabase | project paused after about a week idle; no usable backups | database unreachable until restored |
| Brevo | 300 mails/day | one-time-code mails stop silently |
| Gemini | free quota of the API key | the bot falls back to the canned answer (a human takes over) |
| GitHub Pages / Actions | generous for a public repository | none expected |
